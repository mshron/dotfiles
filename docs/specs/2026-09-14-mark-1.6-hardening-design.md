# mark 1.6: hardening the comment sidecar and the remote mode

**Status:** draft for review. Not implemented.
**Target version:** mark 1.6.0
**Trigger:** the Tribe Bazaar security review of mark 1.5.0 (review `b2525a63`, policy 2026-09-01) recommends "request changes". This spec answers each finding and keeps remote review usable for anyone who installs mark.

## The point

mark 1.6 should make the comment sidecar refuse every request that does not carry a secret token, listen only on the loopback address or the host's Tailscale address, accept only the documents that `mark` has opened, cap request bodies, and pin the Vivify download. These changes close all four findings from the review. They add no new software and no new account setup for remote users. Remote review works over the SSH connection people already use to reach the host. Tailscale is no longer required; it stays available as an option for people who have it.

The preview server (Vivify) itself is out of reach for this version. It has no option to choose its listen address, so it will keep listening on every interface. Section 7 explains the residual risk and the follow-up path.

## 1. What the review found

The review looked at the 1.5.0 bundle. Its findings, in order of severity:

| ID | Severity | File | Finding |
|---|---|---|---|
| ai_1 | high | `comments-server.mjs` | Listens on every interface, allows every origin, has no authentication, and accepts any absolute path from the caller. |
| ai_2 | medium | `comments-server.mjs` | The caller chooses the file. The server reads, rewrites, or deletes the matching `.comments.md` file anywhere the process can reach. |
| ai_3 | medium | `comments-server.mjs` | Request bodies have no size limit. |
| ai_4 | medium | `scripts/setup.sh` | On Linux, setup downloads the latest Vivify release with no pinned version and no checksum. |
| ai_5 | info | `scripts/mark` | Starts detached processes and opens a browser. Expected for this kind of skill. |
| ai_6 | info | `SKILL.md` | Agent instructions match the declared purpose. No blocker. |

All four real findings are correct descriptions of the current code. The sidecar was written for a laptop on a trusted network. Remote mode moved it onto a shared tailnet without changing that design.

## 2. Goals and non-goals

Goals:

- A request to the sidecar without the correct token gets a 401 response and changes nothing.
- The sidecar never listens on `0.0.0.0` or `::`. It listens on `127.0.0.1` in local mode and on the host's Tailscale IPv4 address in remote mode.
- The sidecar reads or writes a comments file only for documents that `mark` has opened in this sidecar's lifetime.
- The sidecar rejects bodies over 64 KiB with a 413 response and closes slow connections.
- The Linux installer downloads one pinned Vivify release and verifies its SHA-256 digest before it installs anything.
- A person on a headless host does the same thing they do today: run `mark <file>`, paste the printed URL into a browser on their own machine. No extra login step and no extra software. Remote access uses SSH port forwarding by default.
- People who prefer Tailscale can keep using it, with the sidecar bound to the tailnet address only.
- `SKILL.md` describes every network and process capability the package uses, so the Bazaar scan can match them against declared behavior.

Non-goals for 1.6:

- Changing where Vivify listens. Vivify has no setting for it. See section 7.
- Encrypting traffic. SSH or Tailscale encrypts the remote path already. Local mode stays on loopback.
- Multiple users commenting on one host. One token per host is enough for the way mark is used.

## 3. Threat model

The sidecar and Vivify run as the user, on a port that other machines may reach.

Who can reach the ports today:

- Local mode: every device on the same network. In a cafe, that is strangers.
- Remote mode: every device on the tailnet, plus the public internet if the host has a public address and no firewall.

Who can reach the sidecar after 1.6:

- Local mode and remote mode over SSH: only processes on the same host. The laptop reaches it through an SSH tunnel.
- Remote mode over Tailscale: only tailnet peers. Tailnet access control rules apply.

What they can do today:

- Through the sidecar: create, edit, or delete `<any file>.comments.md`, and learn whether files exist and when they changed.
- Through Vivify: read any file the user can read, including directory listings.

What 1.6 changes:

- The sidecar port is reachable only from the same machine (local, or remote over SSH), or only from the tailnet (remote over Tailscale).
- Even a tailnet peer cannot use the sidecar without the token.
- Even with the token, a caller can touch only documents that `mark` opened.

What 1.6 does not change: Vivify still listens on every interface, so a tailnet peer or a LAN neighbor can still read files through it. Section 7 covers this.

## 4. Approaches considered

### Approach A: loopback sidecar, SSH forwarding for remote (recommended)

Keep the two servers as they are. Bind the sidecar to loopback. For a remote host, the person forwards the two ports over the SSH connection they already have, so the printed `localhost` URL works unchanged in their own browser. Optionally, bind to the Tailscale address instead for people who have a tailnet. Require a random token on every request except `/health`. Pass the token to the browser in the URL fragment. Limit the sidecar to documents `mark` registered. Add a body limit. Pin Vivify.

- Cost: focused work across three files, plus tests.
- Wins: closes all four findings. No new software, no accounts, no network setup beyond SSH, which every remote user already has. Remote over SSH is the same code path as local mode, so there is less to test. Editors with a remote-SSH mode (VS Code, Cursor) forward loopback ports on their own, so in that setup there is no manual step at all.
- Loses: Vivify still listens everywhere. The token travels in the URL, so anyone who sees the URL can comment. The SSH tunnel lives only while the SSH session lives.

### Approach B: Tailscale Serve as the front door

Bind both servers to loopback. In remote mode, run `tailscale serve` to publish them to the tailnet over HTTPS under one origin. The sidecar checks the `Tailscale-User-Login` header that Serve adds, so only the host's owner can comment.

- Wins: strongest boundary. No secret to manage. HTTPS. Same origin, so no cross-origin headers at all.
- Loses: Vivify cannot bind to loopback today, so the main benefit does not arrive until an upstream change ships. Needs the tailnet admin to enable HTTPS certificates. Needs a one-time `sudo tailscale set --operator=$USER` on Linux. WebSocket pass-through for Vivify's live reload needs a test.

### Approach C: a single front-door proxy

Turn the sidecar into a reverse proxy in front of Vivify. One port, one token, one origin. Vivify moves to loopback behind it.

- Wins: token protects reads through Vivify as well as writes.
- Loses: Vivify still cannot bind to loopback, so the proxy protects nothing until upstream changes. Proxying WebSockets by hand in Node is new, risky code. Much larger change.

### Decision

Approach A for 1.6. It is the smallest change that closes every finding, and it needs nothing a remote user does not already have. Tailscale is not a requirement, which matters for adoption: most people who install mark on a dev box will have SSH and nothing else. Approaches B and C both wait on the same upstream change to Vivify, so 1.6 also files that change (section 7). Approach B becomes a natural 1.7 option for Tailscale users once Vivify can bind to loopback.

## 5. Design

### 5.1 Listen address

`mark.conf` grows one setting. `MARK_LOCATION` stays `local` or `remote`. A new `MARK_REMOTE_ACCESS` says how a browser reaches a remote host: `ssh` (default) or `tailscale`. `mark` turns these into a bind address and passes it to the sidecar in the `MARK_BIND` environment variable.

| Location | Remote access | `MARK_BIND` | URL host printed | Who can reach the sidecar |
|---|---|---|---|---|
| local | n/a | `127.0.0.1` | `localhost` | This machine. |
| remote | `ssh` | `127.0.0.1` | `localhost` | This machine; the laptop through an SSH tunnel. |
| remote | `tailscale` | output of `tailscale ip -4` | the same address | Tailnet peers. `mark` fails if this is empty. |

`ssh` is the default because every remote user has SSH. `tailscale` is the phone path: an iPhone cannot hold an SSH tunnel open while Safari is in front (iOS stops the SSH app within about 30 seconds), but the Tailscale app runs as a VPN and stays up. Section 7.2 has the details. The setup prompt says this in one line so people pick the right one.

In `remote` + `ssh`, `mark` prints the URL and then a hint on the next line:

```text
remote host: forward the ports first, e.g.
  ssh -L 31622:localhost:31622 -L 31623:localhost:31623 <this host>
or add two LocalForward lines to ~/.ssh/config for this host.
```

`SKILL.md` gives the `~/.ssh/config` snippet and notes that VS Code and Cursor remote-SSH sessions forward these ports on their own.

The sidecar calls `server.listen(PORT, MARK_BIND)`. If `MARK_BIND` is missing, it uses `127.0.0.1`. It never accepts `0.0.0.0`, `::`, or an empty string; it exits with an error instead.

`setup.sh` asks the second question only when the first answer is `remote`: "How will your browser reach this host? ssh (default) / tailscale". `MARK_REMOTE_ACCESS` in the environment answers it without a prompt, the same way `MARK_LOCATION` does today.

### 5.2 Token

The token is 32 random bytes, encoded as base64url, about 43 characters.

- The sidecar creates it at first start and stores it in `~/.local/state/mark/token` with mode `0600` (directory mode `0700`). On later starts it reads the file. It regenerates the file if it is missing or unreadable. The file lives outside `~/.config/vivify` on purpose: the install script makes that directory a symlink into the dotfiles checkout, so a secret there would sit beside tracked files.
- `mark` reads the same file after the sidecar is healthy and appends `#ct=<token>` to the URL it prints and opens.
- `comments.js` reads `location.hash` on load, saves the token in `sessionStorage`, and removes the fragment from the address bar with `history.replaceState`. It sends the token on every sidecar request in the header `Authorization: Bearer <token>`.
- The sidecar compares the header with the stored token using a constant-time comparison. Any request other than `GET /health` without a matching token gets `401` and a plain-text body `token required`. `comments.js` shows a one-line notice in the page: "Comments are locked. Run `mark` on this file again and open the new URL."

Why the fragment: browsers never send the fragment to any server, so it does not appear in Vivify's logs or in proxy logs. It does appear in browser history until `replaceState` runs, which happens before any network request. The token is per host, not per document, so one paste works for every document on that host until the file is deleted.

Rotation: delete `~/.local/state/mark/token` and restart the sidecar. `mark` gets a new token on its next run. Document this in `SKILL.md`.

### 5.3 Document allowlist

The sidecar keeps an in-memory set of absolute document paths it will act on.

- New endpoint `POST /register` with body `{ "file": "<absolute path>" }`. It requires the token. The sidecar resolves the path with `fs.realpathSync`, checks that it is a regular file, and adds it to the set. `mark` calls this after the sidecar is healthy, on every run, before it prints the URL.
- Every other endpoint that takes `file` resolves it the same way and requires the resolved path to be in the set. A path outside the set gets `403` and the body `file not registered`.
- The comments file is always `<resolved path>.comments.md`. The caller cannot choose it.
- The set lives in memory only. When the sidecar restarts, it is empty until `mark` runs again. A stale browser tab then sees `403` and shows the same notice as for a bad token.

Why exact files, not a directory root: a root would let a caller pick any sibling file. mark always knows the exact document, so the exact path is the smallest correct rule. This is also the review's own recommendation.

### 5.4 Cross-origin rules

The page comes from Vivify at `http://<host>:<VIV_PORT>`. The sidecar is a different port, so it is a different origin, and cross-origin rules stay.

- `Access-Control-Allow-Origin` is set to exactly `http://<MARK_BIND>:<VIV_PORT>`, never `*`. The sidecar computes this once at start. Through an SSH tunnel the browser's origin is `http://localhost:<VIV_PORT>`, which is the loopback case below.
- `Access-Control-Allow-Headers` adds `Authorization`.
- `Access-Control-Allow-Methods` lists `GET, POST`.
- Requests whose `Origin` header is present and does not match get `403` before any other check.

One catch: people type `localhost`, which is not `127.0.0.1`. When `MARK_BIND` is `127.0.0.1`, the sidecar accepts both `http://127.0.0.1:<VIV_PORT>` and `http://localhost:<VIV_PORT>` as origins. `mark` keeps printing `localhost` in the URL, because that is what works unchanged through an SSH tunnel.

### 5.5 Body limit and timeouts

- `readBody` counts bytes. Over 65,536 bytes, it responds `413` with `body too large` and destroys the socket.
- `http.createServer` gets `{ requestTimeout: 10000, headersTimeout: 5000 }`. Node then closes stalled connections itself.
- Chunked bodies go through the same byte counter, so the limit holds for them too.

### 5.6 Pinned Vivify download

In `setup.sh`, the Linux branch gets two constants near the top:

```bash
VIVIFY_VERSION=0.14.0
VIVIFY_LINUX_SHA256=<digest of vivify-linux.tar.gz for that release>
```

It downloads `https://github.com/jannis-baum/Vivify/releases/download/v${VIVIFY_VERSION}/vivify-linux.tar.gz`, runs `sha256sum -c`, and stops with a clear message on mismatch. It no longer calls the GitHub API for the latest release. Upgrading Vivify means editing the two constants in a reviewed commit. macOS keeps using Homebrew, which verifies its own checksums.

### 5.7 Version handshake

Vivify copies `comments.js` into memory at startup. After an upgrade, the page can run old client code against a new sidecar. To make this visible:

- `GET /health` returns `{ "version": "1.6.0" }` instead of `ok`.
- `comments.js` carries the same version string and compares. On mismatch it shows: "mark was updated. Stop `vivify-server` and run `mark` again."

`mark` keeps using `/health` as a liveness probe; it ignores the body.

### 5.8 Declared capabilities

`SKILL.md` gets a short "What mark runs and connects to" section that lists: two local HTTP servers and their ports and bind addresses, the outbound `tailscale ip` call in remote mode, the outbound Vivify download in the Linux installer with its pinned URL, the browser open, and the files mark writes (`<doc>.comments.md`, `~/.local/state/mark/token`). This is what the Bazaar scan means by "described by the package".

## 7. Residual risks and things this version does not do

### 7.1 Vivify listens everywhere

Vivify's server calls `listen(port)` with no address, which means every interface. It has no configuration key for the address. Anyone who can reach the host's port 31622, on a LAN, a tailnet, or the internet if the host is public and unfirewalled, can read any file the user can read through `http://<host>:31622/viewer/<path>`. SSH forwarding does not change this, because Vivify is still listening on the network addresses too.

1.6 does two things about this:

- `SKILL.md` states it plainly and tells remote users to firewall port 31622 to loopback (and the Tailscale interface, if they use that). This is the same advice as today, kept because it is still the only control.
- We open an upstream pull request to Vivify that adds a `VIV_HOST` environment variable and passes it to `listen`. It is a two-line change. When a release ships with it, mark 1.7 sets `VIV_HOST` from `MARK_BIND`, and Approach B becomes possible.

### 7.2 Phones, and why single-URL tunnels are out of scope

A common way to use mark is from a phone: the agent runs on a VM, the person drives it from the Claude Code or ChatGPT app, and reads the preview in Safari on the same phone. A subagent review on 2026-09-14 checked what reaches a VM from an iPhone without Tailscale:

- Neither the Claude Code mobile app nor Codex on mobile can show a forwarded port or an in-app browser for a remote session. Codex remote hosts are macOS and Windows only, so a Linux VM is not even a supported host there.
- iOS SSH clients (Termius, Prompt) drop the tunnel when you switch to Safari. Blink Shell can keep one alive with its location-tracking trick, but that is a paid app and a workaround.
- Public tunnels (Cloudflare quick tunnels, ngrok, Tailscale Funnel, VS Code dev tunnels) all work from a phone, but each gives one HTTPS URL on port 443. `comments.js` builds the sidecar address as `location.hostname + ':31623'`, so commenting breaks behind any of them. And a public URL exposes Vivify's read-any-file behavior to the internet unless the tunnel itself authenticates (VS Code dev tunnels and Tailscale Funnel do; quick tunnels and free ngrok do not).

So for 1.6: Tailscale is the supported phone path, and `SKILL.md` says so. A tunnel mode is a candidate for a later version. It needs two changes first: the sidecar must be reachable under the same origin and a path as Vivify (a small reverse proxy on the Vivify port, or the front-door design in Approach C), and the token from 5.2 must already be in place. If a tunnel mode is added, prefer Tailscale Funnel or VS Code dev tunnels, which carry their own login, over unauthenticated relays.

## 8. Verification

Automated, in a new `assets/comments-server.test.mjs` run with `node --test`:

1. Start the sidecar on a random loopback port with a temp config directory. Confirm it listens on `127.0.0.1` only.
2. `POST /comment` without a token: expect `401`, and confirm no file was written.
3. `POST /register` with the token for a temp document, then `POST /comment` with the token: expect `204` and the block in `<doc>.comments.md`.
4. `POST /comment` with the token for an unregistered path: expect `403`, no file.
5. Register a symlink that points outside the temp directory: confirm the resolved real path is what gets registered, and the link path alone does not pass.
6. Send a 70 KiB body: expect `413`.
7. Send a request with `Origin: http://evil.example`: expect `403`.
8. `GET /health` without a token: expect `200` and a JSON body with `version`.
9. Start with `MARK_BIND=0.0.0.0`: expect the process to exit non-zero.

Manual, local mode on the laptop:

10. `mark table-test.md` in the in-app browser. Comment on a table row, edit it, delete it. Confirm the address bar has no fragment after load.
11. Open the same URL without the fragment in a second tab. Confirm the locked notice appears and no write succeeds.

Manual, remote mode over SSH on `max.sh.tribe.ai`:

12. Set `MARK_REMOTE_ACCESS=ssh`. `mark --no-open doc.md` on the VM. Open an ssh session from the laptop with the two `-L` forwards. Paste the printed `localhost` URL into the laptop browser. Comment, edit, delete.
13. On the VM, `ss -ltnp | grep 31623` shows only `127.0.0.1`. `curl http://<tailscale ip>:31623/health` from the laptop fails to connect.

Manual, remote mode over Tailscale on the same VM:

14. Set `MARK_REMOTE_ACCESS=tailscale`, restart the sidecar, run `mark --no-open doc.md`. Paste the URL into the laptop browser without a tunnel. Comment, edit, delete.
15. On the VM, `ss -ltnp | grep 31623` shows only the Tailscale address. `curl http://127.0.0.1:31623/health` from the VM fails to connect.
16. Run `setup.sh` on the VM with the pinned digest, then with a wrong digest. The second run must stop before installing.

Bazaar:

17. Resubmit as 1.6.0. Confirm the deterministic scan reports the same capabilities and the AI review no longer lists ai_1 through ai_4.

## 9. Open decisions

These are the choices where I picked a default but you may want a different one.

1. **Token in the URL fragment** (chosen) versus a cookie set by a one-time login link. The fragment is simpler and never reaches a server. A cookie would survive a closed tab, but the login link would put the token in a query string, which servers and proxies log.
2. **Exact document allowlist** (chosen) versus allowing the document's whole directory. The directory version would let one `mark` run cover sibling files, at the cost of letting a caller pick which sibling.
3. **Keep printing `localhost` in the URL** (chosen). It works unchanged through an SSH tunnel, and the sidecar accepts both `localhost` and `127.0.0.1` as origins when bound to loopback.
4. **One token per host** (chosen) versus one per document. Per document means a new paste for every file, which fights the "same as today" goal.
5. **Do the Vivify upstream PR as part of 1.6** (chosen) or leave it for later. It costs little and unblocks 1.7.
6. **Keep the Tailscale variant** (chosen, and now settled by the phone review in 7.2). It is the only path that works from an iPhone without a workaround, so SSH-only is not an option.
